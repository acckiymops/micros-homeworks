# Задача 1: Обеспечить разработку  

## GitLab + GitLab CI (SaaS-версия)

## Архитектура и компоненты
- **GitLab.com** — облачная система контроля версий и CI/CD.
- **GitLab Runners** — собственные агенты сборки (развёрнуты на ваших серверах).


| Требование | Реализация |
|------------|------------|
| Облачная система | GitLab SaaS — не требуется своего хостинга |
| Система контроля версий Git | Встроенная поддержка Git |
| Репозиторий на каждый сервис | Создаётся отдельный проект под каждый сервис |
| Запуск сборки по событию из системы контроля версий | Триггеры в `.gitlab-ci.yml` (push, merge request, tag) |
| Запуск сборки по кнопке с указанием параметров | Ручной запуск pipeline с передачей переменных |
| Возможность создания шаблонов для различных конфигураций сборок | Переменные окружения на уровне pipeline / job |
| Создание шаблонов для различных конфигураций | `include`, `extends`, `!reference`, YAML-якорь |
| Безопасное хранение секретов | **CI/CD Variables** (доступны только для определенных ролей (maintainer, developer, owner)) |
| Несколько конфигураций для сборки из одного репозитория | `rules:`, `only:`, `except:`, матричные сборки (`parallel: matrix`) |
| Кастомные шаги при сборке | Любые shell-команды, скрипты, `before_script`, `after_script` |
| Собственные Docker-образы для сборки проектов | `image: ваш/образ` — из любого доступного registry |
| Возможность развернуть агентов сборки на собственных серверах | **GitLab Runner** (executors: docker, shell, kubernetes, custom) |
| возможность параллельного запуска нескольких сборок | Доступно по умолчанию (зависит от тарифа) |
| возможность параллельного запуска тестов | `parallel: N`, `split tests`, ручное разбиение на джобы |

## Пример взаимодействия

1. Разработчик пушит код в GitLab-репозиторий сервиса.
2. GitLab CI находит `.gitlab-ci.yml` в корне репозитория.
3. Запускается pipeline, джобы выполняются на **GitLab Runner** (поднятом на собственном сервере).
4. Секреты (пароли, токены доступа) подтягиваются из **Protected CI/CD Variables**.
5. Параллельно запускаются тесты (например, 3 джоба с разными наборами тестов).
6. После успешного прохождения тестов — деплой (CI/CD пушит образы в GitLab Container Registry, затем на dev/staging/prod).

## Обоснование выбора

- **Одна платформа** для кода, CI/CD, реестра образов и секретов — минимальное количество точек интеграции.
- **Гибкие шаблоны** — не нужно копировать конфигурации между сервисами.
- **Собственные раннеры** — полный контроль над вычислительными ресурсами, безопасностью и кешами.
- **Параллелизм** из коробки, без необходимости настраивать дополнительные инструменты.

# Задача 2: Логи

## ELK Stack (Elasticsearch + Logstash + Kibana) + Filebeat

## Компоненты

| Компонент | Роль |
|-----------|------|
| **Filebeat** | Лёгкий агент сбора логов со всех хостов из stdout/stderr |
| **Logstash** | Центральный процессор с буферизацией (Persistent Queues) |
| **Elasticsearch** | Центральное хранилище + полнотекстовый поиск |
| **Kibana** | Веб-интерфейс для поиска и дашбордов |

| Требование | Реализация |
|------------|------------|
| сбор логов в центральное хранилище со всех хостов | Filebeat (DaemonSet / systemd) на каждом узле |
| минимальные требования к приложениям, сбор логов из stdout | Приложения пишут в stdout — не нужны библиотеки или API |
| гарантированная доставка логов до центрального хранилища | Logstash Persistent Queues + at-least-once + retry-механизмы |
| обеспечение поиска и фильтрации по записям логов | Elasticsearch Query DSL + Kibana Discovery |
| UI для разработчиков | Kibana (роли, пространства, read-only доступ) |
| Ссылка на сохранённый поиск | Kibana Saved Search → Permalink / Short URL |

## Обоснование выбора

1. **Filebeat** — минимальная нагрузка на хосты, собирает именно из stdout.
2. **Logstash с Persistent Queues** — единственный в популярных решениях даёт **гарантированную доставку** (логи не теряются при отказе Elasticsearch).
3. **Elasticsearch** — лучший в своём классе по скорости и гибкости поиска по логам.
4. **Kibana** — поддерживает сохранённые поиски и ссылки на них.
5. **Зрелость** — стек проверен многими prod системами.
6. **Единая экосистема** — все компоненты от Elastic, полная совместимость.

# Задача 3: Мониторинг

# Решение: Prometheus + Grafana + Node Exporter + Telegraf

## Компоненты

| Компонент | Роль |
|-----------|------|
| **Prometheus** | Сбор, хранение и запрос метрик (Pull-модель) |
| **Grafana** | Визуализация, дашборды, агрегация, алертинг |
| **Node Exporter** | Метрики состояния ресурсов хостов |
| **Telegraf** | Сбор метрик потребления ресурсов сервисов + специфичные метрики |

| Компонент | Что собирает |
|-----------|--------------|
| **Node Exporter** | CPU, RAM, HDD, Network (базовые системные метрики) |
| **Telegraf** | Потребление ресурсов каждым сервисом (CPU, RAM, HDD, Network) + специфичные метрики |

| Требование | Реализация |
|------------|------------|
| Сбор метрик со всех хостов | Prometheus опрашивает Node Exporter и Telegraf на каждом хосте |
| Метрики ресурсов хостов: CPU, RAM, HDD, Network | **Node Exporter** |
| Метрики потребления ресурсов каждого сервиса | **Telegraf** (плагин `procstat` — CPU, RAM, файловые дескрипторы, сетевые соединения) |
| Специфичные для сервиса метрики | **Telegraf** (плагины: `exec` для кастомных скриптов, `http` для опроса `/metrics`, `statsd`, `socket_listener`) |
| UI с запросами и агрегацией | **Grafana Explore** (PromQL) |
| UI с настраиваемыми панелями | **Grafana Dashboards** |

## Обоснование выбора

- **Prometheus** — стандарт для метрик в микросервисной архитектуре.
- **Grafana** — популярный инструмент для визуализации и дашбордов.
- **Node Exporter** — сбор системных метрик хоста.
- **Telegraf** — универсальный агент сбора метрик.
- **Единый язык запросов PromQL** — все метрики из разных источников доступны через один интерфейс.
