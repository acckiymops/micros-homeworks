# Задача 1: API Gateway

## Сравнение решений

| Критерий | Nginx | Kong | Traefik | Spring Cloud Gateway |
|----------|-------|------|---------|---------------------|
| Маршрутизация | ✅ Высокая гибкость, но требует reload при изменениях | ✅ Динамическая через Admin API, без reload | ✅ Автоматическая, нативная для K8s | ✅ Через код, интеграция с Discovery Service |
| Аутентификация | ⚠️ Только Basic Auth. JWT/OAuth2 требуют Lua-скриптов | ✅ Готовые плагины: JWT, OAuth2, Key-Auth, ACL | ✅ ForwardAuth, OAuth2 (Keycloak) | ✅ Spring Security, полный контроль в коде |
| TLS-терминация | ✅ Полная поддержка | ✅ Полная поддержка | ✅ Автоматическая (Let's Encrypt) | ⚠️ Требует внешнего прокси |
| Управление | Файлы конфигурации | Admin API / GitOps (DB-less) | K8s CRD / провайдеры | Код / YAML |
| Производительность | ⚡ Высокая (C) | ⚡ Высокая (ядро Nginx) | ⚡ Высокая (Go) | 🐢 Ниже (JVM) |
| Observability | Базовая, Plus — продвинутая | ✅ Prometheus, OpenTelemetry | ✅ Prometheus, Jaeger | ✅ Micrometer, Actuator |

---

## Выбор: Kong (OSS)

1. Динамическая маршрутизация — добавление/изменение сервисов без перезагрузки через Admin API
2. Готовая аутентификация — плагины JWT, OAuth2, Key-Auth из коробки
3. Высокая производительность — ядро Nginx (OpenResty)
4. Кроссплатформенность — работает на VM, K8s (Ingress Controller), Nomad
5. Наблюдаемость — нативные плагины для Prometheus, OpenTelemetry, Zipkin  

Альтернатива для инфраструктуры на Кубернетес - Traefik как более нативное решение



# Задача 2: Брокер сообщений

## Сравнение решений

| Критерий | RabbitMQ | Apache Kafka | Redis (Streams) | NATS |
|----------|----------|--------------|-----------------|------|
| Кластеризация | ✅ Кластер, очередь-зеркала | ✅ Встроенная (Kafka Cluster) | ✅ Redis Cluster / Sentinel | ✅ NATS Cluster / JetStream |
| Хранение на диске | ✅ Да (очереди durable) | ✅ Да (сегменты логов) | Частично (RDB/AOF, но не основное назначение) | ✅ Да (JetStream) |
| Скорость | Средняя (50K msg/s) | Высокая (100K+ msg/s) | Очень высокая (1M msg/s) | Высокая (100K+ msg/s) |
| Форматы сообщений | Любой (bytes, JSON, protobuf) | Любой (bytes) | Любой | Любой |
| Разделение прав | ✅ Виртуальные хосты, пользователи, ACL | ✅ ACL по темам (авторизация через плагины) | ⚠️ Простое (пароль, ACL ограничены) | ✅ Пользователи, разрешения (субъекты/публикация) |
| Простота эксплуатации | Простой, много документации | Сложный (ZooKeeper/KRaft, настройка) | Простой | Простой (один бинарник) |
| Модель доставки | Очередь (push) | Лог (pull) | Stream (push/pull) | Core: push, JetStream: pull |
| Гарантии доставки | At-most-once / At-least-once | Exactly-once (с 0.11) | At-most-once / At-least-once | At-least-once / Exactly-once (JetStream) |

---

## Выбор: Apache Kafka

Требование | Как выполняет Kafka
-----------|--------------------
Кластеризация | Нативная репликация партиций, лидер/фолловеры. При отказе узла данные не теряются.
Хранение на диске | Все сообщения хранятся на диске с настраиваемым сроком хранения (retention). Даже при перезапуске данные сохраняются.
Высокая скорость | До сотен тысяч msg/s. Благодаря batch-обработке, zero-copy, последовательной записи на диск.
Разные форматы | Принимает любые байты. Сериализация через Avro, Protobuf, JSON.
Разделение прав | ACL управляются через `kafka-acls.sh` или Admin API.
Простота эксплуатации | ⚠️ Компромисс. Сложнее RabbitMQ, но современные инструменты (KRaft вместо ZooKeeper, CMAK, Kowl) упрощают.

### Дополнительные преимущества

- Ретеншн по времени/размеру — храним историю сообщений, можно перечитывать заново
- Consumer groups — управление смещениями, балансировка нагрузки между потребителями
- Масштабирование — добавляем брокеры и партиции без остановки

### Недостатки

- Задержки — не для real-time (миллисекунды, а не микросекунды)
- Сложность на старте — требует понимания партиций, смещений, retention
- Маленькие сообщения неэффективны — batch-оптимизация под поток данных
